## What is SRE?

Site Reliability Engineering (SRE) is a software engineering discipline applied to operations. Created by Google, it combines software development with systems administration to create highly reliable and scalable systems.

<Callout type="info" title="Fundamental Principle">
  "SRE is what happens when you ask a software engineer to design an operations function." - Ben Treynor, VP of Engineering @ Google
</Callout>

### Defining Effective SLOs

```yaml
# Example SLO specification
slo:
  name: "Main API"
  description: "SLO for the production API"

  indicators:
    - name: availability
      type: ratio
      good_events: 'http_requests_total{status=~"2..|3.."}'
      total_events: 'http_requests_total'

    - name: latency
      type: threshold
      metric: 'http_request_duration_seconds'
      threshold: 0.2  # 200ms
      percentile: 99

  objectives:
    - indicator: availability
      target: 99.9
      window: 30d

    - indicator: latency
      target: 99.0
      window: 30d

  error_budget:
    calculation: "100% - SLO target"
    # 99.9% availability = 0.1% error budget
    # In 30 days = ~43 minutes of allowed downtime
```

## Error Budgets

Error Budget is the amount of "error" allowed before violating the SLO. It's a tool to balance reliability and innovation speed.

### Error Budget Calculation

```
Error Budget = 100% - SLO Target

Example for 99.9% availability SLO in 30 days:
- Error Budget = 0.1%
- Minutes in month = 30 * 24 * 60 = 43,200 minutes
- Budget in minutes = 43,200 * 0.001 = 43.2 minutes

If consumed 20 minutes with incidents:
- Remaining budget = 43.2 - 20 = 23.2 minutes
- Budget consumed = 46%
```

### Error Budget Policies

```yaml
error_budget_policy:
  # When budget is healthy (< 50% consumed)
  healthy:
    actions:
      - "Prioritize features and innovation"
      - "Experimentation allowed"
      - "Normal deployments"

  # When budget is in warning (50-80% consumed)
  warning:
    actions:
      - "Reduce deployment frequency"
      - "Prioritize bug fixes"
      - "Increase change reviews"

  # When budget is critical (> 80% consumed)
  critical:
    actions:
      - "Feature freeze"
      - "Bug fixes only"
      - "Everyone focuses on reliability"

  # When budget is exhausted
  exhausted:
    actions:
      - "Total deployment freeze"
      - "Mandatory postmortem"
      - "Executive action required"
```

<Callout type="success" title="Benefit">
  Error budgets transform the tension between "move fast" and "be reliable" into a data-driven decision.
</Callout>

## Incident Management

### Incident Severities

| Severity | Impact | Response | Example |
|----------|--------|----------|---------|
| **SEV1** | Service completely down | Immediate, all-hands | Main API not responding |
| **SEV2** | Significant degradation | < 15 min | Latency 10x above normal |
| **SEV3** | Limited impact | < 1 hour | Secondary feature broken |
| **SEV4** | Minimal | Business hours | Cosmetic bug in production |

```markdown

- **Date**: 2025-01-02

- **Severity**: SEV2

- Alerts detected the problem in 15 minutes
- Rollback was executed in less than 10 minutes
- Clear communication during the incident

## What didn't work
- Load tests didn't cover the scenario
- DB dashboard wasn't visible to the team

| Item | Owner | Deadline |
|------|-------|----------|
```

### Burn Rate Alerts

```yaml
# Alerts based on burn rate (error budget consumption)
groups:
  - name: slo-alerts
    rules:
      # Alert if burning budget 14x faster than normal
      # (would consume all budget in ~2 days)
      - alert: SLOErrorBudgetBurnHigh
        expr: |
          (
            sum(rate(http_requests_total{status=~"5.."}[1h]))
            /
            sum(rate(http_requests_total[1h]))
          ) > (14 * 0.001)  # 14x the budget rate of 0.1%
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "High error budget burn rate"

      # Alert if burning 3x faster (would consume in ~10 days)
      - alert: SLOErrorBudgetBurnMedium
        expr: |
          (
            sum(rate(http_requests_total{status=~"5.."}[6h]))
            /
            sum(rate(http_requests_total[6h]))
          ) > (3 * 0.001)
        for: 30m
        labels:
          severity: warning
```

<Callout type="warning" title="Avoid Alert Fatigue">
  If the team ignores alerts because there are too many false positives, you have a serious problem. Each ignored alert is a risk.
</Callout>
